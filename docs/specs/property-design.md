# 매물(property) 도메인 — Frontend 구현 현황 정리

## 배경 / 성격

`auth-design.md`/`user-design.md`와 같은 성격의 **요구사항 명세서 대비 실제 구현 대조 문서**입니다.

**범위**: `app/(main)/properties/**`, `app/services/properties.ts`, `app/mappers/property.ts`만 다룹니다. 실거래가 비교(market-data)와 허위매물 의심 신호(risk-analysis)는 별도 도메인이라, 이 문서에서는 "Property 화면이 그 데이터를 어떻게 다루는가"만 언급하고 그 도메인 자체의 정확성은 다루지 않습니다.

## 주요 화면 / 파일

| 파일 | 역할 |
| --- | --- |
| `app/(main)/properties/page.tsx` + `PropertiesClient.tsx` | 매물 목록 — 검색/필터 |
| `app/(main)/properties/register/page.tsx` | 매물 등록 폼 |
| `app/(main)/properties/[id]/page.tsx` + `PropertyDetailClient.tsx` | 매물 상세 — 수정/삭제/신고 진입점 |
| `app/(main)/properties/[id]/edit/page.tsx` + `PropertyEditClient.tsx` | 매물 수정 폼 |
| `app/(main)/properties/[id]/PropertyReportModal.tsx` | 매물 신고 모달 |
| `app/services/properties.ts` | `GET/POST /properties`, `GET/PATCH/DELETE /properties/{id}`, `POST /properties/{id}/reports` |

## 매물 등록 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 주소 입력 | ⚠️ **일반 텍스트 입력일 뿐, 주소 검색 기능이 없음** — `<input>` 하나에 자유 텍스트로 주소를 직접 타이핑해야 함. 사용성 요구사항의 "주소 검색 기능 제공"과 배치됨 |
| 주택 유형/거래 유형/가격 입력 | ✅ 유형은 버튼 선택, 거래 유형에 따라 보증금만/보증금+월세 입력란이 동적으로 바뀜(`isMonthlyRent`) |
| 매물 사진 선택 입력 | ❌ **입력 UI 자체가 없음** — 등록 폼에 이미지 업로드/URL 입력 필드가 전혀 없다. 상세 화면(`PropertyDetailClient`)은 `imageUrls`를 표시할 준비가 되어 있는데, 애초에 사진을 넣을 방법이 없어 항상 "등록된 사진이 없어요"로만 표시됨 |
| 설명 선택 입력 | ✅ |
| 필수 입력값 확인 | ✅ 주소/보증금/면적(+월세 거래 시 월세) 각각 클라이언트에서 사전 검증 |
| 거래 유형에 맞는 가격 정보 확인 | ✅ 월세 거래인데 월세 미입력 시 별도 에러 |
| 주소 정규화 + 좌표 변환 | Backend 책임 — FE는 텍스트 주소를 그대로 보내고 응답의 좌표를 신뢰 |
| 동일 조건 매물 중복 등록 확인 | Backend 책임 — FE는 실패 시 일반 에러 문구만 표시, 중복 여부를 사전에 안내하지 않음 |
| 매물유형이 단독/다가구면 시세 매칭 정확도 저하 안내 | ✅ `propertyType === 'DETACHED_HOUSE'`일 때 안내 문구 노출 |
| 성공: 매물 등록 + 시세 비교 제공 | ⚠️ **등록 성공 시 상세(`/properties/{id}`)가 아니라 목록(`/properties`)으로 이동함.** 코드 주석엔 "상세 화면이 아직 실제 API 응답 형태에 안 맞춰져 있어서"라고 적혀 있는데, 실제로 `PropertyDetailClient`는 이미 `PropertyDetailResponseDto`를 그대로 소비하도록 되어 있어 이 주석이 최신 상태를 반영하는지 재확인이 필요함(남은 이슈 참고) |
| 부분 성공: 시세 조회 실패 시 별도 상태 안내 | ✅ 응답의 `notice` 필드를 쿼리 파라미터로 목록 화면까지 전달해 배너로 표시 |
| 실패: 필수값 누락/잘못된 가격/주소 식별 실패/미지원 유형/중복 등록/이미지 오류 | ⚠️ 전부 동일한 "매물 등록에 실패했습니다" 문구 하나로 처리 — 실패 사유별 구분 없음(이미지 오류는 애초에 이미지 입력이 없어 발생 불가) |

## 매물 목록 조회 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 인증된 사용자 소유 매물만 조회 | ✅ Backend가 인증 쿠키 기준으로 필터링해 응답 |
| 지역/면적/거래유형/주택유형/가격 범위로 검색 | ✅ `PropertiesClient`의 지역 검색창(region, 도로명/지번주소 부분일치) + 거래유형 필터 칩(전체/전세/월세) + "상세 필터" 패널(매물유형/면적범위/보증금범위, 거래유형이 월세일 때만 월세금액범위도 노출)이 URL 쿼리파라미터로 `getProperties`에 전달되고, BE `PropertySearchCondition`으로 실제 서버사이드 필터링됨. 기존엔 클라이언트에서 현재 페이지 내용만 걸러내던 방식이었는데 서버사이드로 전환됨 |
| 정렬 조건 적용 | ❌ 정렬 기능 없음 — Backend가 내려준 순서(최근 등록순으로 추정) 그대로 표시 |
| 삭제된 매물 제외 | Backend 책임(ACTIVE 상태만 응답) — FE는 별도 필터링 없이 그대로 신뢰 |
| 페이지네이션 | ✅ BE가 `PageResponse`로 응답이 바뀌면서 `getProperties(cookieHeader, { page })`가 `page`/`size`/`sort` 쿼리 파라미터를 지원하게 됨. `PropertiesClient`에 이전/다음 페이지 링크(`?page=N`) 추가, 페이지 이동 시 현재 필터 조건도 그대로 유지됨(`buildPageHref`) |
| 성공: 목록 + 지도 마커 | ⚠️ 목록 카드는 나오지만 지도 마커 표시는 이 화면에 없음(상세 화면에만 `KakaoMap` 있음) |
| 확인 필요 신호 개수 / 전세가율 배지 | ✅ `PropertiesClient`/`PropertyListItem`의 조건부 렌더링은 이전부터 있었으나, BE 응답(`PropertyListItemDto`)에 필드 자체가 없어 항상 "준비 중"만 보였음 — BE에 `checkSignalCount`/`signalSummary`/`jeonseRatio` 필드가 추가되면서 실제 값으로 연동됨. `jeonseRatio`는 BE가 percent 정수만 내려주는 컨벤션이라 FE 타입을 `string`→`number`로 정정하고 "%" 포맷팅을 FE에서 붙이도록 수정(`getJeonseRatioDisplay`) |
| 검색 결과 없음 → 빈 목록 | ✅ "조건에 맞는 매물이 없습니다" 문구 |
| 실패: 인증 실패/잘못된 검색 조건 | ✅ 인증 실패는 `(main)/layout.tsx`가 상위에서 처리(Auth 문서 참고). "잘못된 검색 조건"(면적/보증금/월세 범위의 최소값이 최대값보다 큰 경우)은 BE의 `PROPERTY_INVALID_SEARCH_CONDITION` 에러 메시지를 그대로 화면에 노출 |

## 매물 상세 조회 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 매물 존재/접근 권한 확인 | Backend 책임 — FE는 응답 실패 시 "매물을 찾을 수 없습니다"로 통합 표시 |
| 기본 정보 + 주소 정보 조회 | ✅ |
| 실거래가 비교 결과 조회 | ✅ `priceHistory`/`marketDelta` 있으면 차트로, 없으면 "아직 실거래가 비교 정보가 없어요" |
| 위험 신호·안전성 정보 조회 | ✅ **연동됨.** `PropertyDetailResponse`엔 관련 필드가 없지만, `page.tsx`가 매물 상세를 불러올 때 `GET /risk-signals`/`GET /deposit-safety`를 별도로 호출해 `PropertyDetailClient`의 "확인 필요 신호"/"보증금 안전성" 카드를 채운다. 목록은 N개 매물을 한 번에 다뤄야 해서 `PropertyListResponse`에 요약 필드를 넣었지만, 상세는 매물 1건만 보면 되므로 별도 API 호출 2건으로 충분해 이렇게 설계된 것으로 보임. 한 번도 계산된 적 없는 매물(`depositSafety.status === 'notChecked'`)이면 `POST /risk-analysis`를 자동 트리거해 계산 후 다시 조회 |
| 임장 체크리스트 생성 여부 확인 | ✅ BE 응답의 `checklistCreated`를 반영해 버튼 문구가 "현장 체크리스트 시작" / "현장 체크리스트 이어보기"로 갈림 |
| 누적 신고 여부(존재 유무) 조회 | ✅ BE 응답의 `reported`(본인 신고 여부)를 반영해 신고 버튼이 비활성화되고 "이미 신고한 매물이에요" 배너가 뜸. 이번 세션에서 막 신고한 경우(`reportSuccess`)도 동일하게 취급 |
| 신고 내용 원문/신고자 정보 비노출 | N/A — 신고 여부(boolean)만 받아오고 신고 내역 자체는 조회하지 않으므로 노출될 것도 없음 |
| 실패: 존재하지 않는 매물/삭제된 매물/접근 권한 없음 | ⚠️ 세 사유 모두 "매물을 찾을 수 없습니다"로 동일하게 표시 — 구분 없음 |

## 매물 수정 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 등록자 본인 확인 | Backend 책임 |
| 입력값 검증 | ✅ 보증금/면적(+월세) 클라이언트 사전 검증 |
| **주소 변경 시 재정규화·좌표 재계산** | ❌ **주소 자체를 수정할 수 없음.** 화면에 "주소와 매물·거래 유형은 등록 시 확정된 값이라 수정할 수 없어요. 변경이 필요하면 매물을 새로 등록해주세요"라고 명시돼 있고, `UpdatePropertyRequestDto`에도 주소/유형 필드 자체가 없음 |
| **주소·가격·보증금·거래유형 변경 시 시세/위험신호 재계산** | ⚠️ **가격/보증금 변경 시 재계산은 되지만, 주소·거래유형은 애초에 수정 대상이 아니라서 그 갈래는 발생 자체가 불가능.** 요구사항 문서는 4가지 필드 전부가 수정 가능하다고 전제하는데, 실제로는 가격 계열(보증금/월세)과 면적/설명만 수정 가능한 구조 — 요구사항과 구현의 전제 자체가 다름(남은 이슈 참고) |
| 성공: 매물 수정 + 재계산 결과 갱신 | ✅(범위 내에서) — 수정 성공 시 상세로 이동, 재계산은 Backend 응답을 그대로 신뢰 |
| 부분 성공: 재계산 실패 시 "재계산 필요" 상태 표시 | ⚠️ 확인 불가 — FE가 이 상태를 구분해서 보여주는 코드가 없음(응답 DTO에 이런 상태 필드가 있는지부터 Backend 문서 확인 필요) |
| 실패: 존재하지 않는 매물/수정 권한 없음/잘못된 입력값/주소 식별 실패 | ⚠️ "매물 수정에 실패했습니다" 단일 문구. "주소 식별 실패"는 애초에 주소를 안 보내니 발생 불가 |

## 매물 삭제 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 등록자 본인 확인 | Backend 책임 |
| 삭제 상태로 변경(논리 삭제) | ✅ `DELETE /properties/{id}` 호출, 성공 시 목록으로 이동 |
| 삭제 확인 절차 | ⚠️ 앱 디자인 시스템에 이미 `Modal` 컴포넌트가 있는데(신고 모달에서 사용), 삭제 확인은 브라우저 네이티브 `window.confirm()`을 씀 — 기능은 하지만 스타일이 통일돼 있지 않음 |
| 삭제된 매물과 연결된 체크리스트/위험신호를 화면에서 조회 못하게 처리 | Backend 책임(체크리스트 쪽은 오늘 FK 전환하면서 확인함 — `checklist-overview-list-design.md` 참고). FE는 매물 목록/상세 API가 삭제된 매물을 안 내려준다고 가정 |
| 성공: 목록/상세에서 제외 | ✅ |
| 실패: 존재하지 않는 매물/삭제 권한 없음/이미 삭제된 매물 | ⚠️ "매물 삭제에 실패했습니다" 단일 문구 |

## 매물 신고 — 요구사항 대비

| 요구사항 | 실제 구현 |
| --- | --- |
| 신고 사유 선택(+기타 직접 입력) | ✅ 5가지 사유 라디오 버튼, "기타" 선택 시 텍스트 영역 노출 |
| 매물 존재/신고 가능 상태 확인 | Backend 책임 |
| 동일 사용자 중복 신고 확인 | ✅ **응답의 `error.code === 'REPORT_DUPLICATE'`를 구분해서 "이미 신고한 매물이에요"로 별도 표시** — 이 도메인에서 유일하게 실패 사유를 구체적으로 구분하는 사례 |
| "기타" 사유 텍스트 길이 검증 | ⚠️ 빈 값인지만 확인(`detail.trim().length === 0`), 최대 길이 제한은 클라이언트에 없음(`<textarea>`에 `maxLength` 없음) |
| 신고 접수 상태 저장 | ✅ |
| "중복 등록" 신고와 risk-analysis 자동 탐지를 문구·위치로 구분 | ✅ 신고 사유는 "동일 매물이 중복 등록됐어요"(사용자 제보), 화면의 "확인 필요 신호" 섹션은 별도 카드로 분리돼 있어 구조적으로 섞이지 않음 |
| 성공: 접수 완료 안내 | ✅ 모달 닫힘 + 상세 화면에 초록색 안내 배너 |
| 실패: 존재하지 않는 매물/삭제된 매물/중복 신고/사유 누락/기타 길이 초과 | ⚠️ 중복 신고만 구분되고 나머지는 일반 에러 문구("신고 접수에 실패했습니다")로 뭉뚱그림. 사유 누락은 클라이언트에서 미리 막음 |

## 비기능 요구사항 — 대조

| 항목 | 요구사항 | 실제 |
| --- | --- | --- |
| 본인 매물만 조회/수정/삭제 | O | Backend 책임, FE는 응답을 신뢰 |

## 요구사항에 없던 추가 구현

- 등록/수정 폼의 금액 입력값에서 쉼표(`,`)를 제거하고 숫자로 파싱하는 처리 — 사용자가 "180,000,000"처럼 입력해도 허용
- 등록/수정 폼의 보증금/월세/전용면적 입력란에 타이핑 중 자릿수 콤마를 자동으로 붙여서 표시(`app/lib/numberFormat.ts`) — 위 파싱 처리와 쌍을 이룸
- "면적" 라벨을 상세 화면과 동일하게 "전용면적"으로 통일(등록폼/수정폼/목록 필터 패널)
- 등록/수정 제출 중 로딩 오버레이 추가(`app/ui/LoadingOverlay.tsx`) — 등록은 국토부/카카오 실거래가 조회, 수정도 동일한 재계산을 거쳐야 응답이 오는 동기 구조라 몇 초씩 걸릴 수 있어서, 그 동안 폼 카드 위에 스피너+안내 문구를 덮어 진행 중임을 보여주고 입력 필드/버튼을 비활성화함
- 전세/월세 가격 표기 단위 통일(`formatDepositText`, `app/mappers/property.ts`) — 예전엔 전세는 "9,000만원"처럼 단위가 붙는데 월세만 "보증금 3,000 / 월세 55"처럼 단위 없이 숫자만 나와서 표기가 안 맞았음. 월세 쪽도 동일한 `formatManwon`을 쓰도록 통일해 "보증금 3,000만원 / 월세 55만원"으로 표시됨

## 남은 이슈 / 확인 필요 총정리

1. **매물 등록 폼에 사진 입력 UI가 없음** — 요구사항은 "선택적으로 매물 사진을 입력"한다고 되어 있고 상세 화면은 표시 준비가 되어 있는데, 애초에 넣을 방법이 없다. 파일 업로드/URL 입력 중 어느 쪽으로 갈지 방향이 필요함(User 도메인의 프로필 사진과 같은 결정이 필요)
2. **등록 성공 후 목적지가 상세가 아니라 목록** — 코드 주석은 "상세 API가 아직 실제 응답 형태에 안 맞다"고 되어 있는데, 실제로 `PropertyDetailClient`는 이미 real API DTO를 그대로 소비하는 것처럼 보인다. 주석이 낡은 건지, 아직 못 옮긴 이유가 따로 있는지 확인 필요
3. **매물 수정에서 주소·거래유형을 아예 수정 불가로 막아둔 것이 요구사항과 전제 자체가 다름** — 요구사항은 "주소 변경 시 재정규화" 같은 흐름을 전제하는데, 실제 설계는 "주소/유형 바뀌면 재등록"이다. 요구사항 쪽을 수정할지, 지금 설계(재등록 유도)를 공식 정책으로 문서화할지 팀 논의 필요
